## 2. 指标（只看三个）

### 指标 1 ｜意向数 —— **主指标** ✓

- **定义**：一条**真实的外部答案**（表单走 mailto 发出的那封邮件，或主动发到收件邮箱的意向信）。
  它至少含三题答案中的第 1 题（愿不愿意押）。
- **只认这个**：它要求对方**付出一个真实动作**（把邮件发出去），是本轮唯一能回答"愿不愿押钱"的证据。
- **排除**：我们自己的测试邮箱（`pledge-test-*@example.com`、`live-visitor-*@example.com`）、任何 `@example.com`、
  我们自己的地址、以及本地自测写进 `pledge-signups.jsonl` 的记录。
- **去重**：同一邮箱/同一封邮件重复只算 1 个。

### 指标 2 ｜"愿意押"的条数 —— 主指标里最关键的一档 ✓

- 三题里第 1 题选**「愿意押」**的条数，**单独计**，这才是判定线的依据。
- 「看情况」**不计入**"愿意押"，**但也不丢掉** —— 报告里单列，因为它是"钩子还没打对"的线索。
- 第 2 题与第 3 题是**质量校验**：选了「愿意押」却**既没选押给谁、也没选押多少**的，
  在报告里标记为「弱意向」，与"三题都答"的分开列。

### 指标 3 ｜落地页访问数 —— 我们**读不到** ✗（如实声明）

**读不到，原因是硬的、不是懒：**
- 托管在 **GitHub Pages 静态站点**，服务端不提供访问日志给我们；
- 页面**刻意不加载任何第三方统计脚本**，所以也没有第三方口径；
- 我们**不打算为了这个数字去加统计** —— 那会往页面上塞追踪代码，与本项目的红线冲突。

→ **任何报告里出现具体访问数，都是编的。** ✗
**能拿到的弱替代**：各平台文章的阅读量/浏览量。它是"看过文章"的数，**不是"看过落地页"的数**，
两者**必须分开列、不混算**。

## 3. 判定线（D0+14 结算，必须落到其中一条）

| 判定 | 条件（**"愿意押"的条数**） | 结论 | 建议动作 |
|---|---|---|---|
| ✅ **有戏** | **≥ 10** | 有真实的人**愿意为这件事押钱** | 值得投入做**承诺契约原型**（担保人模式，我们绝不碰钱），用这批人做首批内测 |
| 🟡 **苗头不足** | **3 ~ 9** | 有火苗，但不足以证明"一类人普遍如此"，也可能只是好奇 | **不投产品，换钩子再测一轮**：换入口语境（连亏加倍 / 半夜那一笔）或换人群，再跑 14 天 |
| 🔴 **到此为止** | **≤ 2** | 多个渠道投放之后，**几乎没有人愿意押** | **止损**：不再往这个方向投人力 |

### 判定线是怎么来的（不是事后拍的）

- 上游数据给的先验：明确写「我知道不该做但还是做了」的只有 **0.5%（20/3,889）**；
  主动想被管住的只有 **0.2%（9/3,889）**。→ 这是**很薄的证据**，所以门槛不能定高。
- 假设看到页面的人里愿意押的比例 p 在 **0.5% ~ 1%** 量级（比"留邮箱"更重的动作，p 更小），
  14 天若有约 1,000~2,000 次有效触达，期望"愿意押"≈ **5 ~ 20** → **10** 落在"本该看到"的量级。
- **≤ 2 的含义**：在 p=1%、触达 1,000 的零假设下，观测到 ≤2 的概率 ≈ 12%；而如果连**否定的答案都没有几条**，
  说明**渠道根本没触达**（那时不许用 ≤2 下结论，要按 §1 记为「无效渠道」）。
- **前置声明纪律**：**只声明这一条线**。事后若想改，必须写清：改了什么、为什么改、
  以及**在拿到数据之前**的理由 —— 不许挑对自己有利的门槛。

### 附加证据（不改判定线，只作补充）

- **≥3 条"愿意押"且明确指定了担保人/慈善机构** → 即使总数 3~9，也按"有戏"一侧处理（含信息量高）。
- **≥3 条主动来信问"什么时候能用/多少钱"** → 同上。
- **0 条愿意押 + 0 封来信** → 强化"到此为止"结论。
- **「看情况」占压倒多数** → 不是"有戏"也不是"没戏"，是**钩子没打对**，按 🟡 处理并换语境再测。

## 4. 数据采集方式

| 数据 | 采集方式 | 可信度 |
|---|---|---|
| 意向（线上） | 访客在页面上点提交 → 打开一封填好的邮件 → 他按发送 → 落到收件邮箱 `760808632@qq.com` → **每轮开工读一次邮箱**（硬动作约束 `read-boss-mail-every-turn`），当天手工记进 `pledge-signups-log.md` | **高**（真实动作） |
| 意向（本地自测） | 本地收集器 `pledge-collector.mjs`（127.0.0.1:8793）把表单 POST 落盘到 `pledge-signups.jsonl` | 自测用，**不计入真实意向** |
| 平台阅读量 | 各平台文章页自显示的浏览数，手工抄录 | **中**（不是落地页访问数） |
| 落地页访问数 | **读不到** ✗（见 §2 指标 3） | 无 |

**⚠ 本方案最大的诚实缺口（必须一直写在报告里）**：
**我们没有分母。** 只有分子（几条意向），不知道多少人看过页面 —— 所以**无法计算转化率**，
也**不能说"转化率低/高"**。所有结论只能建立在**绝对数**上。

## 6. 每次汇报的硬格式（不许含糊）

| 项 | 值 | 来源 | 状态 |
|---|---|---|---|
| 今日**愿意押**条数 | N（没有就写 **0**） | 收件邮箱 | 已确认 / 未核 |
| 今日全部意向条数（愿/不愿/看情况） | N | 收件邮箱 | |
| 累计（去重） | N | `pledge-signups-log.md` | |
| 主动来信 | N 封 | 收件邮箱 | |
| 落地页访问数 | **读不到** | — | — |
| 平台阅读量（分开列） | dev.to X / 自家站 Y | 各平台页面 | |
| 判定 | 进行中 / 有戏 / 苗头不足 / 到此为止 | 本方案 §3 | |

**三条汇报纪律**：
1. **数字必须有来源**（约束 `numbers-must-cite-source-20261006`）：说不出"从哪来的、样本多大"，就不许写进报告。
2. **区分三档语气**：【已确认】= 两个来源一致 / 直接读原始记录；【初步】= 单一来源；【推测】= 我的推理。不许混排。
3. **单位是"条"不是"人"、不是"客户"** —— 我们只看到一封邮件，无法确认背后是谁。报告写"N 条意向"，不写"N 个人要买"。

## 7. 未做到 / 做不到（如实声明）

1. **读不到落地页访问数** → **永远没有转化率**，只能看绝对数。
2. **线上表单不能直接落盘**（静态站无后端）→ 登记要走邮件，**多一步人工发信会漏掉一部分意向**
   （有些人不会去点那封邮件）。这是本方案已知的最大漏损。
3. **无法验证答案真实性**（可能有人乱填、同行好奇）→ 缓解：主动来信可看出端倪；数量本身分不出。
4. **无法自动判定"他说的愿意押是真是假"** —— 愿意押是一个**声明**，不是行为。
   本轮只能测"意愿"，**不能测"实际会押"**；真要验证得等原型（且那一步涉及钱，红线先卡住）。
5. **入口语境是本轮的核心假设，不是已验证事实**：我们认为"挂在他刚立完规矩的那一刻"比当广告发有效，
   **这一点本轮拿不到对照数据**（同一批人只能测一次）。所以 D0+14 若为苗头不足，第一件该改的就是入口语境。
6. **判定线是设计参数，不是客户调研**（p=0.5%~1% 是我们的假设）→ 已写明假设与推导，便于后人推翻重定。
