## 2. 指标（只看三个，别的都不算数）

### 指标 1 ｜落地页访问数 —— 我们**读不到** ✗

**如实说明：读不到。** 原因是硬的、不是懒：
- 落地页托管在 **GitHub Pages 静态站点**，服务端不提供访问日志给我们；
- 页面**刻意不加载任何第三方统计脚本**（Google Analytics 之类一律没有），所以也没有第三方口径；
- 我们**不打算为了这个数字去加统计**——那会往页面上塞追踪代码，与"不采集隐私"的自定红线冲突。

→ **落地页访问数这一项，本方案明确标为「读不到」。任何报告里出现具体访问数，都是编的。** ✗

**能拿到的替代分母（弱）：** 各平台文章的**阅读量/浏览量**（dev.to 有公开阅读数、CSDN/掘金有浏览量）。它是"看过文章"的数，**不是"看过落地页"的数**，两者不能等同——报告里必须**分开列、不混算**。

### 指标 2 ｜意向登记数 —— 这是**主指标** ✓

- 定义：**真实的外部邮箱**留下登记（页面表单提交，或发登记邮件到收件邮箱）。
- **只认这个**：它需要对方**付出一个真实动作**（填邮箱并同意），是三个指标里最硬的"有人要"的证明。
- **排除**：我们自己的测试邮箱（`intent-test-*@example.com`）、任何 `@example.com` 地址、我们自己人的地址。
- **去重**：同一邮箱重复登记只算 1 个。

### 指标 3 ｜主动来信数 ✓

- 定义：对方**主动联系**（邮件提问、问"什么时候能用"、问"多少钱"、说"我需要这个"）。
- 不限于通过落地页来的 —— 从任何渠道来的主动联系都算（回复文章、邮件）。
- **单独计，不与指标 2 合并**：来信的信息量高得多（会说出他的真实痛点），值得单独看。

## 3. 数据采集方式（能测什么、不能测什么，写清楚）

| 数据 | 采集方式 | 可信度 |
|---|---|---|
| 意向登记（邮件） | 有人发出登记邮件 → 落到收件邮箱 `760808632@qq.com` → **每轮开工读一次邮箱**（已有硬动作约束 `read-boss-mail-every-turn`），把当天的登记手动记进 `intent-signups-log.md` | **高**（真实动作） |
| 意向登记（表单） | 页面表单在**线下/自测**时会把邮箱写到 `intent-signups.jsonl`（本地收集器 `intent-collector.mjs`）。**线上没有后端**，线上提交走 mailto 兜底（见 §6 场景 B 实测） | 线上=走邮件，同上一行 |
| 平台阅读量 | 各平台文章页自己显示的浏览数，手工抄录 | **中**（不是落地页访问数） |
| 落地页访问数 | **读不到** ✗（见 §2 指标 1） | 无 |

**⚠ 本方案最大的诚实缺口（必须一直写在报告里）**：
**我们没有分母。** 只有分子（几个登记），不知道有多少人看过页面 —— 所以**无法计算转化率**，也**不能说"转化率低/高"**。所有结论只能建立在**绝对数**上（"14 天内有 N 个人真的留了邮箱"）。

**为什么量很小也是有效证据**：我们预期"每个看到页面的人愿意留邮箱"的概率 p 只有 **1%~5%** 这个量级（这是一个**收款前的意向**，不是一个免费下载）。在 p=2%、看过页面的人 N≈540 的零假设下，14 天的期望登记数 ≈ **10.8 个**。也就是说：**如果需求真的存在、渠道也真的触达了人，我们本该看到 10 个上下**。所以下面的判定线不是拍的。

## 4. 判定线（D0+14 结算，三条线，必须落到其中一条）

| 判定 | 条件 | 结论 | 建议动作 |
|---|---|---|---|
| ✅ **需求存在** | **真实意向 ≥ 10 个**（同一邮箱去重后） | 有真实的人**愿意为这件事付出动作** | **值得投入改产品** —— 立刻做承诺契约原型（冷静期 / 24h 冷却 / 担保人），用登记名单做首批内测 |
| 🟡 **弱信号** | **3 ~ 9 个** | 有火苗，但不足以证明是"一类人的普遍问题"，也可能只是熟人/同行好奇 | **不投产品，先改钩子再测一轮**：换备选文案（连亏加倍 / 重启失效），或换聚焦的人群（如只在夜盘人群里测），再跑 14 天 |
| 🔴 **需求不成立，建议止损** | **≤ 2 个** | 在两个交易周内、多个渠道投放之后，**几乎没有人愿意留下一个邮箱** | **建议止损**：不再往这个方向投人力。理由见下 |

### 为什么止损线定在「≤ 2 个」

- **统计上**：按 §3 的零假设（p=2%，期望 10.8），14 天只观测到 ≤2 个，纯属"其实没人要"的可能 ≈ 0.13% —— 也就是说，**这个结果几乎不可能是运气不好导致的**，它就是"没人要"。
- **即使门槛压到最保守**（p 只有 1%）：期望 5.4 个，观测到 ≤2 个仍落在"需求不存在"一侧（P(X≤2) ≈ 11%）。
- **判定规则前置声明（重要）**：**我只预先声明这一条判定线**（"期望≈10 个"）。我**不**在事后挑选对自己有利的门槛 —— 那是数字造假的另一种形式。若事后想改判定线，必须写清：改了什么、为什么改、以及**在拿到数据之前**的理由。

### 主动来信的加权（不修改上面的线，只作补充证据）

- **≥3 封主动来信**（且不是熟人）→ 即使登记数只有 4~9 个，也**按"需求存在"一侧处理**：来信含的信息量高，说明痛点真实。
- **0 封来信 + 登记 ≤2** → 强化止损结论。
- 来信**不能**反向否定（不能因为有人问价就说需求存在而忽略登记数 = 0）。

## 5. 每次汇报的硬格式（不许含糊）

每份汇报必须按这个表填，**读不到就写「读不到」**：

| 项 | 值 | 来源 | 状态 |
|---|---|---|---|
| 今日真实意向登记 | N 个（没有就写 **0**） | 收件邮箱 | 已确认 / 未核 |
| 累计真实意向登记（去重） | N 个 | `intent-signups-log.md` | |
| 主动来信 | N 封 | 收件邮箱 | |
| 落地页访问数 | **读不到** | — | — |
| 平台阅读量（分开列） | dev.to X / CSDN Y | 各平台页面 | |
| 判定 | 进行中 / 需求存在 / 弱信号 / 止损 | 本方案 §4 | |

**三条汇报纪律**：
1. **数字必须有来源**（约束 `numbers-must-cite-source-20261006`）：说不出"从哪来的、样本多大"，就不许写进报告。
2. **区分三档语气**：【已确认】= 两个来源一致 / 直接读原始记录；【初步】= 单一来源；【推测】= 我的推理。**不许混排。**
3. **本单位是"个"不是"人"** —— 我们只看到一个邮箱，无法确认背后是不是一个人。报告里写"N 个邮箱登记"，不写"N 个人要买"。

## 6. 落地页的自动化自测（每次上线前必跑）

`intent/form-test.mjs`（无头 Edge 实测，**不是模拟**）：

| 场景 | 内容 | 结果 |
|---|---|---|
| **A 采集器在线** | 表单真的 **POST** 到本地收集器 → 邮箱**真的落盘**到 `intent-signups.jsonl` → 页面显示登记成功 | **16/16 通过** |
| **B 采集器离线**（= 线上 GitHub Pages 的真实形态） | 走 **mailto 兜底**：登记邮件被正确打开，收件人/主题/正文全部预填正确 | **17/17 通过** |

复现：
```
node intent\intent-collector.mjs 8791      # 终端 1（本地收集器）
node intent\form-test.mjs                  # 场景 A
node intent\form-test.mjs --no-server      # 场景 B
```

**线上为什么必须走 mailto**：GitHub Pages 是纯静态托管，**没有服务端**，任何 POST 都无处可去。所以线上的真实通道是"打开一封已填好的登记邮件，由访客自己按下发送"。页面上写明了这一点。**我们不假装线上有后端。** ✗

## 7. 未做到 / 做不到（如实声明）

1. **读不到落地页访问数**（无服务端日志、刻意无第三方统计）→ 因此**永远没有转化率**，只能看绝对数。
2. **表单在线上不能直接落盘**（静态站无后端）→ 实际登记要走邮件，多一步人工发信，**会损失一部分意向**（有些人不会去点那封邮件）。这是本方案已知的最大漏损。
3. **无法验证邮箱是否真实有效**（可能有人乱填）→ 缓解：报告里把"邮箱域名明显可疑"的单列，但不擅自剔除。
4. **无法区分"同行好奇"与"真实客户"** → 缓解：主动来信可看出端倪；登记数本身分不出。
5. **判定线是设计参数，不是客户调研**（p=1%~5% 是我们的假设）→ 已写明假设值与推导，便于后人推翻重定。
